# Разработка и локальная проверка

Открытый репозиторий проекта: [roboroddom/opencode-smart-context](https://github.com/roboroddom/opencode-smart-context). Собственный код лицензирован под 0BSD; сторонний MIT-фрагмент сохраняет NOTICE. Этот документ описывает воспроизведение проверок.

## Среда и команды

Текущая проверенная среда: Linux, OpenCode V1 `1.18.35`, Bun `1.2.5`, npm `10.9.7`. TypeScript и остальные зависимости закреплены в `package.json` и `bun.lock`. `opencode` должен быть в `PATH`; альтернативный абсолютный путь можно передать через `OPENCODE_BIN`.

В рабочем каталоге проекта:

```sh
bun install --frozen-lockfile
bun run check
bun run check:package
```

- `check` проверяет типы, внутренние ссылки документов и JSON-примеры, четыре проверки чистой логики и шесть сценариев настоящего локального сервера OpenCode с подставным провайдером.
- `check:docs` отдельно проверяет внутренние ссылки и синтаксис примеров конфигурации.
- `test:e2e` запускает только серверные сценарии.
- `check:package` выполняет `npm pack` во временный каталог, проверяет точный состав, распаковывает архив, устанавливает зависимости с `--frozen-lockfile`, затем повторяет серверные сценарии с **распакованным** плагином. Публикации и изменений глобальной конфигурации нет. Установка зависимостей и их загрузка провайдером OpenCode могут требовать сети; это не запросы к модели по подписке.

Тесты печатают пути временных каталогов. Они оставляют логи для разбора ошибки и завершают запущенный сервер после прогона. Для проверки другого локального комплекта исходников предназначена `OPENCODE_CONTINUITY_PLUGIN_DIR`; путь к `index.ts` берётся из этого каталога. Пользовательские HOME/XDG-каталоги и состояние помощника для сервера заменяются тестовыми.

Пример выбора двоичного файла:

```sh
OPENCODE_BIN=/ABSOLUTE/PATH/opencode bun run check
```

## Что доказывают тесты

- Отсутствие инструкции и инструмента при выключении до первого сообщения.
- Обновление контекста, продолжение и сохранение истории в базе.
- Восстановление после перезапуска без повторного поручения; выключение после границы.
- Подтверждение, отказ и отмену новой сессии при уточнении во время разрешения.
- Чистая функция проверяет ожидание активных инструментов, изменение хеша, отсутствующую границу и учёт кеша.

Это не полная проверка аварий в каждой фазе, двух конкурирующих процессов, всех пользовательских разрешений или ошибок на реальном техническом пределе. Сценарии используют заранее заданные ответы подставной модели: они проверяют механику плагина, а не способность настоящей модели выбирать удачный момент и писать достоверный HANDOFF.

## Ручная проверка панели

```sh
bun run test:ui
```

Команда открывает настоящий OpenCode с обеими частями плагина и отдельными временными настройками. Не нужно создавать внешний JSON-файл. Для проверки содержимого другого архива задайте `OPENCODE_CONTINUITY_PLUGIN_DIR`.

При ручной проверке проверьте начальный индикатор, `/continuity`, включение/выключение, показатели до/после ответа, историю и состояния ошибок. Отправка сообщений может использовать выбранную вами модель; автоматическая подставная модель здесь не запускается.

## Устройство проекта

| Файл | Назначение |
| --- | --- |
| `index.ts` | Серверные хуки, инструмент и применение перехода |
| `core.ts` | Чистое решение по выбранному переходу, преобразование отправляемой истории и показатели |
| `store.ts` | Настройки, снимки, атомарное сохранение и локальные блокировки |
| `tui.tsx` | Панель, индикаторы и ручная просьба подготовить обновление |
| `CONTEXT-CONTINUITY-PROMPT.md` | Правила для основной модели, загружаемые при старте |
| `tests/` | Проверки логики, реального сервера и ручной запуск панели |
| `scripts/check-package.ts` | Проверка состава и серверной загрузки из архива |

## Зависимости и упаковка

Поставка — исходники `.ts`/`.tsx`, которые загружает OpenCode; `dist` не создаётся. Все четыре модуля, инструкция и стороннее уведомление должны находиться рядом. `files` в `package.json` задаёт разрешённый состав; тесты, локальные настройки, база, журналы и `node_modules` в архив не входят.

`@opencode-ai/plugin` используется сервером во время выполнения (помощник `tool`), `solid-js` — панелью, `@opentui/solid` — преобразованием JSX в OpenCode. `@opentui/core` и `@opentui/keymap` сохранены как закреплённые зависимости интерфейсного окружения и peer-зависимости SDK. TypeScript и `@types/bun` нужны проверкам. Переклассификация зависимостей в peer или их обновление требуют отдельной проверки загрузчика; сами версии и группы в этой работе не менялись.

В архив включены обе версии README, остальные документы и `bun.lock` для воспроизводимой локальной установки, но не средства разработки из `tests/` и `scripts/`. Команды разработки из `package.json` выполняются в исходном репозитории; архив предназначен для подключения плагина.

Автоматическая проверка `.github/workflows/check.yml` запускает типы, тесты и упаковку на Linux с OpenCode `1.18.35`. [Первый запуск на GitHub](https://github.com/roboroddom/opencode-smart-context/actions/runs/37626838224) прошёл успешно. Workflow не содержит публикации.

## Перед возможным выпуском

1. Определить целевую версию OpenCode и способ установки.
2. Проверить метаданные `roboroddom/opencode-smart-context`, LICENSE (0BSD) и сохранность MIT-уведомления в NOTICE.
3. Повторить `check` и `check:package` на выбранной версии OpenCode; проверить **обе части** из архива в изолированной конфигурации, получить проверку отображения владельцем.
4. После явного разрешения на конкретный способ установки проверить Git/npm-подключение и только затем написать его команды в README.
5. Перед публикацией сверить состав и версию.
